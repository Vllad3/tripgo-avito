# TripGo Service

Сервис поездок TripGo: создание, получение и завершение поездки. Лабораторная работа 1 курса «Разработка микросервисов на Go».

## Требования

- Go 1.24+ (инструменты подключены через `go get -tool`)
- Docker (для локального окружения)
- `tripgoctl` — утилита курса, см. [course-infra](https://github.com/course-go-autumn-2026/course-infra)
- `psql` — опционально, для ручной проверки базы

## Запуск

```bash
tripgoctl cluster start        # один раз на машине
tripgoctl environment start    # поднимает PostgreSQL и создаёт .env
make migrate                   # накатывает миграции
make run                       # запускает сервис
```

Сервис слушает `HTTP_ADDR` (по умолчанию `:8080`).

Проверка:

```bash
curl -i localhost:8080/health
curl -i localhost:8080/ready
```

## Цели Makefile

| Цель | Что делает |
|---|---|
| `make run` | запускает сервис |
| `make migrate` | накатывает все миграции (goose up) |
| `make migrate-down` | откатывает последнюю миграцию (goose down) |
| `make generate` | генерирует типы и chi-сервер из OpenAPI в `internal/generated/` |

`make` подключает сначала `.env.example` (значения по умолчанию), затем `.env` (адреса из `tripgoctl`), поэтому второй перетирает первый. `.env` создаётся `tripgoctl` и в git не попадает.

## Переменные окружения

Все переменные обязательны: если какая-то не задана или длительность не больше нуля, сервис падает на старте с понятной ошибкой.

| Переменная | Пример | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | адрес HTTP-сервера |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` | время на чтение заголовков запроса |
| `HTTP_READ_TIMEOUT` | `10s` | время на чтение всего запроса |
| `HTTP_WRITE_TIMEOUT` | `15s` | время на обработку и запись ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | время жизни простаивающего keep-alive соединения |
| `LOG_LEVEL` | `info` | уровень логирования |
| `SHUTDOWN_TIMEOUT` | `10s` | бюджет на graceful shutdown |
| `DATABASE_URL` | из `.env` | строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS` | `10` | максимум соединений в пуле |
| `DATABASE_MIN_CONNS` | `2` | минимум соединений в пуле |
| `DATABASE_MAX_CONN_LIFETIME` | `30m` | время жизни соединения |
| `DATABASE_CONNECT_TIMEOUT` | `5s` | таймаут на `Ping` при старте |
| `DATABASE_QUERY_TIMEOUT` | `3s` | таймаут на каждый запрос в БД |

Переменные `HTTP_*_TIMEOUT` добавлены сверх базового набора курса, чтобы не хардкодить таймауты сервера. Имена базовых переменных не менялись.

## API

Контракт — `contracts/openapi/trip-service.openapi.yaml`. В этой работе реализованы:

| Метод | Путь | Ответы |
|---|---|---|
| `POST` | `/api/v1/trips` | 201, 400, 409, 500 |
| `GET` | `/api/v1/trips/{tripId}` | 200, 400, 404, 500 |
| `POST` | `/api/v1/trips/{tripId}/finish` | 200, 400, 404, 409, 500 |
| `GET` | `/health` | 200 |
| `GET` | `/ready` | 200, 503 |

Ошибки отдаются по RFC 9457 (`application/problem+json`) с полем `code`: `invalid_request`, `trip_not_found`, `trip_completed`, `driver_busy`, `internal_error`.

## Структура

```
cmd/trip-service/        main: сборка зависимостей и запуск
internal/config/         чтение и проверка переменных окружения
internal/database/       пул pgx и менеджер транзакций
internal/domain/         доменная модель поездки
internal/repository/     репозитории trips и trip_status_history (pgx + squirrel)
internal/handler/        HTTP-ручки, валидация, problem+json
internal/httpserver/     http.Server с таймаутами и роутером chi
internal/generated/      код, сгенерированный из OpenAPI (не править руками)
migrations/              миграции goose
contracts/               контракты курса (не редактируются)
```

## Решения

### Уровень изоляции: READ COMMITTED

Транзакция в сервисе нужна ради атомарности нескольких записей (поездка и запись в журнале статусов), а не ради согласованного чтения многих строк. От гонок защищают ограничения базы, а не изоляция:

- две активные поездки одного водителя запрещены уникальным индексом;
- двойное завершение исключено условием `status = 'active'` прямо в `UPDATE`.

Уровень задаётся в одном месте, в `TxManager.Do`.

### Менеджер транзакций

`TxManager.Do(ctx, fn)` открывает транзакцию, кладёт её в `context` и вызывает `fn` с этим контекстом. Если `fn` вернула `nil`, делается `COMMIT`; если ошибку или случилась паника — `ROLLBACK`, ошибка возвращается, паника пробрасывается дальше.

Репозитории не получают транзакцию аргументом. Они берут исполнителя из контекста через `database.ExecutorFromContext`: если в контексте есть транзакция, запрос идёт через неё, если нет — через пул. `pgx.Tx` и `*pgxpool.Pool` приводятся к общему интерфейсу `Executor` (`Exec`, `Query`, `QueryRow`).

Вложенный `Do` не открывает вторую транзакцию: если в контексте уже есть транзакция, он просто вызывает `fn`. Вызов репозитория вне `Do` выполняется через пул, каждый запрос — отдельной автотранзакцией.

Откат выполняется с `context.WithoutCancel`, чтобы он дошёл до базы, даже если контекст запроса уже отменён.

### Запрет двух активных поездок на водителя

Частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX trips_unique_driver_id_idx ON trips (driver_id) WHERE status = 'active';
```

Обычный `UNIQUE (driver_id)` не подходит: он запретил бы водителю иметь больше одной поездки вообще, включая завершённые. Индекс проверяется базой при вставке, поэтому правило держится при параллельных запросах: из двух одновременных `INSERT` один получает ошибку `23505`. Репозиторий распознаёт её по коду и имени индекса и возвращает доменную ошибку `ErrDriverBusy`, которая превращается в `409 driver_busy`.

Проверка «сначала прочитать, потом вставить» в коде не использовалась: между чтением и вставкой остаётся окно, в которое проходит параллельный запрос.

### Завершение поездки без гонки

```sql
UPDATE trips SET status = 'completed', finished_at = now()
WHERE id = $1 AND status = 'active'
```

Проверка статуса и запись происходят в одном операторе, окна между ними нет. Если затронуто 0 строк, дополнительное чтение различает «поездки нет» (`404`) и «уже завершена» (`409`). Два одновременных `finish` дают один `200` и один `409`, `finished_at` не перезаписывается.

Завершение, запись в журнал и чтение обновлённой поездки для ответа выполняются в одном `Do`.

### /health и /ready

`/health` отвечает `200`, пока процесс жив, и не ходит в базу: иначе недоступность базы заставила бы оркестратор перезапускать здоровый процесс. `/ready` пингует базу и отвечает `503`, если она недоступна: так оркестратор перестаёт слать трафик, но процесс не перезапускает.

### Прочее

- Сгенерированный код лежит в `internal/generated/`, как указано в команде генерации в тексте работы 1.
- Ошибки переводятся в HTTP-коды в одном месте, в `handler.writeError`. Внутренние детали (текст ошибки БД) пишутся в лог, клиенту уходит общий текст.
- Невалидный `tripId` обрабатывается сгенерированным кодом; его обработчик ошибок заменён, чтобы ответ тоже был `problem+json`.
- Время в ответах всегда в UTC.
- `id` и `started_at` поездки генерирует сервис.

## Проверки

- `goose down` откатывает обе миграции;
- `/ready` отдаёт `503` при остановленном PostgreSQL и `200` после старта;
- по `SIGTERM` сервис дожидается текущего запроса и выходит в пределах `SHUTDOWN_TIMEOUT`;
- при падении второй вставки в `trips` ничего не остаётся;
- 20 одновременных созданий на одного водителя дают один `201` и девятнадцать `409`;
- 20 одновременных завершений одной поездки дают один `200` и девятнадцать `409`.

## Известные ограничения

- Если координаты не переданы в запросе, после разбора JSON они становятся `0, 0`, а это валидная точка. Отличить «не передано» от «передан ноль» без указателей или отдельного валидатора схемы нельзя.
- Поля `finished_at` и `last_position_at` в ответе опускаются, когда пусты (в контракте они необязательные).
